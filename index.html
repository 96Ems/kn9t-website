why kn9t?

Most coding agents optimize for convenience.
kn9t optimizes for knowing what happened.

  • Every durable action is recorded.
  • Every session can be replayed.
  • Tools and policies are replaceable.
  • The model is not the architecture.

01 — what it is

An agent you can read back afterwards.

kn9t is a single-user, localhost coding agent written in Rust. It talks to your model, runs tools, and streams to a terminal UI or to any HTTP client — while writing every durable fact to a log you can replay months later.

  • Events are the truth — one enum is the SSE frame, the SQLite row, and the input that reconstructs the session. They are the same bytes.
  • Everything is a plugin — tools, providers, policy, compaction, subagents and MCP bridges run as subprocesses. The core grows seams, not features.
  • Auditable by construction — an append-only SQLite log you can query with the sqlite3 CLI; folding it rebuilds any session exactly.
  • Any model — OpenAI-compatible endpoints, Anthropic, or your own provider plugin. Prices are hand-written per model and frozen at write time.
  • Scriptable — JSONL on stdout, a localhost HTTP API, and --json output made for jq.
  • One writer, N readers — lease-based sessions: three clients can watch a session over SSE while one drives it.
  • No async runtime — OS threads and plain fn traits. tokio-free by construction.

02 — how it works

One turn, end to end.

Six steps, one thread that may spend money. Everything else holds trait objects and never calls a provider.

01lease

Your prompt arrives with the session's write lease. Watchers stream over SSE and never need one.

02plan

plan_request() folds the log into a provider request: repairs tool args, closes orphaned calls, compacts past ~80% of the window, places cache breakpoints.

03stream

The provider does wire mapping only. Retry is allowed before the first byte, never after — you have already seen something.

04policy

Every tool call is voted on by policy plugins — Allow, Ask, Deny, Replace. The strictest vote wins, so load order cannot change the outcome.

05commit

Durable facts are written in one transaction — seq assigned inside it — then broadcast. The log never waits on a queue.

06idle

Even an abort closes every tool call with a result. The transcript never contains an orphaned tool call — the one shape providers reject.

Durable events carry a seq and are never lost; transient ones (stream deltas, progress) may be — losing them is self-healing. Publishing an unpersisted durable event is a compile error, not a code-review comment.

That was the trailer. ▸ architecture.html is the full tour — read from the source with file:line citations: the event log, state as a fold, the SSE attach protocol, the plugin wire, and exactly how hot reload works.

Attach order is the whole trick: read first and you can miss whatever lands between the read and the subscription. There is a deterministic regression test for that race — and a script asserting the test actually runs.

03 — design

Primitives, not features.

Nothing user-facing is built in. What other agents bake into the core, kn9t ships as plugins — so the core stays minimal and the behaviour stays yours.

No built-in tools bash, read, edit, write ship as the kn9t-tools plugin.
No built-in safety Risk judgement is a policy plugin. With none installed, everything is allowed — deliberately, and documented.
No built-in compaction A plugin picks keep / summarize / drop per tool call, using the session's own model and budget.
No built-in subagents They are real sessions spawned through the host API — visible, forkable, and billed where the work happened.
No MCP in the core Bridged by a plugin. The core doesn't know the protocol exists.
No async runtime One active provider stream does not need futures. Threads and plain fn, no .await anywhere.
No model registry Prices are hand-written per model — a later price change can never rewrite what you already spent.
No second wiring path The TUI speaks HTTP only and cannot link the core, so interactive and scripted modes cannot drift apart.

Every phase of a turn is a seam, including the ones that decide what happens next.

writing one, in rust

use kn9t_plugin_sdk::{Tool, ToolCtx, ToolOutput, CancelToken, wire::ToolSpec};
use serde_json::{json, Value};

struct MyTool;

impl Tool for MyTool {
    fn spec(&self) -> ToolSpec {
        ToolSpec {
            name: "my_tool".into(),
            description: "does X".into(),
            schema: json!({"type": "object", "properties": {"path": {"type": "string"}}}),
            parallel_safe: true,
            hidden: false,
        }
    }

    fn execute(&self, args: &Value, ctx: &ToolCtx, cancel: &CancelToken)
        -> Result<ToolOutput, String>
    {
        ctx.progress.send("starting…");              // streams as ToolProgress
        if cancel.is_cancelled() { return Err("cancelled".into()); }
        Ok(ToolOutput { content: vec![], is_error: false })
    }
}

The SDK has zero workspace dependencies and is publishable — a third-party plugin needs nothing from this repo.

providers are plugins too

A provider is either in-process (OpenAI-compatible) or a subprocess plugin — kn9t-anthropic adds the Anthropic Messages API to kn9t without touching the core. Same door for MCP (kn9t-mcp bridges Jira, GitHub and friends), for agent skills (kn9t-skills) and for project instructions (kn9t-agents-md injects your AGENTS.md into context).

05 — honesty

The honest limits.

Every project says what it does. Here is what kn9t does not do for you — drawn from its own findings list, not softened.

− read before you run it
−Not a sandbox. Tools run with your privileges. Install kn9t-policy before giving an agent anything you care about.
−Secrets aren't redacted. A key read from a .env lands in the transcript and in the log, verbatim.
−Single user, localhost. One writer per session by design — not a server for a team.
−Pre-1.0. The config format and plugin protocol may still change before the first stable release.

The engineering-level findings — known debt, refactor targets, rejected alternatives — live where they belong: ARCHITECTURE.md §14 and DESIGN.md.

06 — getting started

Get running in 60 seconds.

The goal is your first kn9t — not a systems lecture. Three commands and you're talking to it:

# 1 · get it (rust 1.98+)
$ git clone https://github.com/96Ems/kn9t && cd kn9t
$ cargo build --release

# 2 · run it — first launch writes ~/.kn9t and starts the server
$ ./target/release/kn9t

# 3 · type a prompt in the box. that was your first kn9t.

The default tools come with it. Models, real prices, more tools and your own plugins are the next block — after your first turn.

07 — faq

Questions people ask first.

What is kn9t, exactly?

A single-user coding agent that runs on your machine: a Rust server holding the model conversation, the tool loop and an append-only session log; a terminal UI; and a localhost HTTP API so anything can drive it. Everything user-facing — tools, policy, compaction — is a subprocess plugin.

Is it free?

Yes — MIT, no strings. You bring a model: an API key or a subscription endpoint. There is no generated model registry and no telemetry, so your spend is whatever your provider bills, tracked to the cent in the log.

Does it phone home?

No. The only outbound traffic is to the model provider you configure. Inbound, the server listens on loopback only, rejects any request carrying an Origin header, and requires a bearer token on every call. Verified the hard way — a hostile web page, in a real browser, holding a stolen token: nothing gets through, nothing leaks back.

Which models can I use?

Anything OpenAI-compatible, Anthropic, or anything you wrap in a provider plugin — in-process or subprocess. Provider quirks (max-tokens field, system role, reasoning form, cache headers) are declared in config.

Why no async?

The workload is a handful of modules around one active provider stream, not 10k connections. Blocking I/O keeps every trait a plain fn returning a value — and the whole loop testable offline against replayed raw provider bytes.

Is it ready for daily use?

It is pre-1.0: expect config and plugin-protocol changes before the first stable release. v1 is implemented and verified end to end, with 1000+ tests — but read the honest limits first.
