how kn9t works▌

A tour of the internals — read from the source, then checked against the docs. Every claim cites a file and a line, so you can open the repo and follow along. The one idea everything else follows from: state lives in an append-only event log, never in process memory — which is exactly why the UI, the plugins and the config can all hot reload while a session is running.

01 — the one rule

The log is the truth

Every durable fact of a session is one Event appended to a SQLite table. The SSE wire, the database, and what you see on screen are the same stream. The module doc says it in two lines: 

//! Events are the durable log: session state is reconstructed by folding events in seq order.
//! Each variant is marked as durable (carries `seq`) or transient (live only).

One enum, two tiers. The wire format is internally tagged, snake_case event.rs:115-118: #[serde(tag = "kind", rename_all = "snake_case")]. 7 durable variants carry seq and fold in order; 19 transient variants are live-only and never persisted — the store rejects them outright: "append: transient event rejected" session.rs:20-22.

the table

CREATE TABLE IF NOT EXISTS events (
  session_id TEXT    NOT NULL REFERENCES sessions(id),
  seq        INTEGER NOT NULL,
  ts         INTEGER NOT NULL,
  kind       TEXT    NOT NULL,
  payload    TEXT    NOT NULL,
  PRIMARY KEY (session_id, seq)
);

Append-only in practice: the only statements that touch events are INSERT and SELECT (the single exception is whole-session deletion session_delete.rs:59-74). Projections (messages, usage) are derived tables that can always be rebuilt from this one.

one append = one transaction, then — and only then — a broadcast

  1. BEGIN IMMEDIATE, then seq = head_seq + 1 for the session — gapless by construction. “The store owns seq assignment: stamp it before serializing and projecting” session.rs:33-47
  2. INSERT INTO events, project rows, blob refcounts, UPDATE sessions SET head_seq, COMMIT session.rs:51-85
  3. Then the after-append observer fires outside the connection lock: “the callback must never block or deadlock other store users” session.rs:87-94. That observer is the single publisher to the SSE bus: “durable events reach the bus only through this observer … one publisher, no duplicates” state.rs:221-226

persist first, broadcast second — a subscriber can never see an event the log doesn't have.

02 — state reconstruction

State = fold(events)

Nothing keeps authoritative session state in memory. Reads are derived — incrementally projected on write, and rebuilt from scratch by replay whenever something needs to start clean. The code's own words are fold and replay.

  • Projector — kn9t_store::project::project maps one durable event to rows (Message, Usage, Compacted) project.rs:96-173. session_forked, model_changed, handoff, tools_toggled project nothing.
  • Replay — replay_events runs SELECT session_id, ts, payload FROM events ORDER BY session_id, seq and folds every payload through a closure reproject.rs:156-193. Unknown kinds are skipped with a warning — old readers stay compatible with a newer log.
  • Last-wins — model and disabled tools are reconstructed by taking the newest relevant event: last ModelChanged > model_at_fork > SessionForked.fork.model_at_fork session.rs:170-211, and tools_toggled always carries the full list so a replay is idempotent session.rs:149-168.
  • Honest log, usable read — when the model needs its context, plan_request folds the projection and repairs it in memory only: unparseable tool args are mended and orphaned tool calls are closed with a synthesized result — “the log stays honest, the read is made usable” plan.rs:95-100, 234-289.

why this is the hot-reload enabler

Because state is a fold over an append-only log and not a pile of process memory, any piece of the system can be torn down and rebuilt from a cursor: the TUI re-attaches at last_seq, a plugin re-declares its tools, the config swaps its providers. There is nothing to migrate and nothing to rehydrate — the log is the state. Reload can't corrupt what reload doesn't own. §07 shows the three reload surfaces in detail.

04 — the runtime

Threads, not futures

//! Blocking, thread-per-connection over `tiny_http`; no tokio, no async (GI-5, R-SRV-015).

and the paranoia is structural

05 — live streaming

SSE: no gap, no duplicate

A client can attach at any point — cold boot, reconnect after a dropped Wi-Fi, a second terminal — and must see the transcript exactly once, in order. GET /session/{id}/events?from={seq} guarantees it with an attach protocol whose ordering “is exact and is the whole point of this module” sse.rs:3-16:

1 · subscribefirst — buffer the bus
2 · replaydurable seq > from
up to head_seq
3 · live_partialthe in-flight text
4 · dedup flushdrop seq ≤ head_seq
then go live
  1. Subscribe first, buffering everything from now on. “Read-then-subscribe is forbidden: a durable event committed in the gap between the read and the subscribe would be lost” sse.rs:7-14
  2. Replay durable rows past the client's cursor, read through one atomic store snapshot “so a concurrent append cannot commit between the two reads” sse.rs:162-174 · db.rs:214-258
  3. Emit the in-flight partial from live_messages — best-effort; the authoritative MessageAppended supersedes it sse.rs:71-76, 122-125
  4. Flush the buffer, discarding any event with seq ≤ head_seq — exact dedup, because durable seqs are gapless sse.rs:127-152

the watermark, and the one case it can't cover

head_seq is the dedup watermark: everything at or below it already went out in step 2. But the subscriber ring is bounded and drops the oldest frames on overflow — and durable echoes ride it too. A lost durable event would be “a permanent hole in the client's transcript unless it refetches”, so the prelude tracks contiguous_through and emits an explicit event: gap frame telling the client to re-snapshot sse.rs:86-106 · router.rs:323-335.

Reconnects are then trivial: keep a seq cursor, re-attach with ?from=last_seq. The TUI's reducer is a pure (State, SseFrame) → State that tracks last_seq so a reconnect never re-renders old events kn9t-tui/src/reducer.rs:1-7, 55.

06 — the extension model

Plugins are processes

A plugin is any executable speaking newline-delimited JSON over stdin/stdout — “every message is exactly one JSON object on one \n-terminated line” kn9t-plugin/src/codec.rs:1-6. Rust, Go, Python, TypeScript: the wire doesn't care. Even the built-in tools are a plugin — “Tools are loaded from the kn9t-tools plugin subprocess, not from an in-process crate — this validates the full plugin code path” kn9t-server/Cargo.toml:11-12.

kn9t-serverthe host
host ▸ plugin · hello · hook · event · cancel · shutdown · kv_result · api_result
plugin ▸ host · hello · result · chunk · done · event · kv_get/set/del · request · declare

The handshake is one round: the host sends Hello { proto: 1, kn9t: <version> }, the plugin answers Hello { name, capabilities, hooks, tools, events, provider } — anything else is "expected hello from plugin" tools.rs:277-315. After that, tool calls are streaming "tool_call" round-trips (300s deadline, cancellable), provider calls "provider_complete" remote_tool.rs:82-96 · remote_provider.rs:48-52.

07 — hot reload

Hot reload, without the asterisks

Three surfaces reload while kn9t is running. None of them can corrupt state, because none of them own it (§02): the log is the truth, and reloadable things are pure derivation — a Lua sandbox, a tool registry, a provider map.

surfacetriggercode pathautomatic
the UI

~/.kn9t/config.toml		 mtime poll every 2s (debounced) · POST /config/reload state.reload_config() state.rs:847 yes

the UI — save the file, watch the screen

  1. Save anything in ~/.kn9t/tui/ (or ~/.kn9t/tui.lua). An notify watcher — per-file and per-directory, covering modify / create / remove — fires after a 100ms debounce kn9t-tui/src/lua/watcher.rs:71-97, 165-179.
  2. The sandbox is reset: runtime.reload() re-applies the sandbox (io, loadfile, dofile are nil; load rejects bytecode sandbox.rs:27-160), reinstalls the lazy accessors, and republishes the theme — “republishing picks up a theme change without a restart” mod.rs:425-446.
  3. Built-in first, yours second. reload_all() re-runs the embedded default UI, then your files: “Re-running the built-in means deleting a function from your config restores the default behaviour instead of leaving the previous definition stale in the Lua state” mod.rs:402-417.
  4. Caches and bindings are rebuilt — the render cache is force-invalidated mod.rs:270-277, plugin panels are cleared panels.rs:274-275, and keymaps / clicks / commands are re-drained “so kn9t.map picks up on hot-reload” app.rs:712-741.
  5. A Tick wakes the loop, the next frame renders the new tree — against the same Rust state (transcript, session, scroll: untouched). And a Lua error never kills anything: “A Lua error (syntax or runtime) never crashes the TUI … Hot-reload continues watching for fixes” mod.rs:24-27 — you get the error shell naming the failing chunk, and saving again fixes it.

what survives: the Rust App state and the lazy message store — “the sandbox is rebuilt, the store is not” mod.rs:78-82.

a plugin — the reload contract

/// Hot-reload a plugin by declared name (R-PLUG2-100): cancel in-flight calls, wait for
/// `done`, `shutdown`, respawn from the same `cmd`, then re-handshake and re-register.
/// Calls that miss the shutdown get a synthetic error at the call site.
1 · cancelevery in-flight call
2 · drain≤ 30s, poll 20ms
3 · shutdownclose the pipe
4 · respawnsame cmd · re-hello
registry rebuilt
  1. Cancel every in-flight call state.rs:578-581 — plugins that declared cancelable see a Cancel {id}.
  2. Drain up to the before_tool_call timeout (30s), polling every 20ms; leftover calls are abandoned with a log line state.rs:583-594.
  3. Shutdown the old process and close the write pipe state.rs:596-599.
  4. Respawn from the same cmd, full hello-handshake, and wire the new host “the same path as a freshly loaded one — they cannot drift” state.rs:601-618.
  5. Rebuild the whole ToolRegistry from all hosts (dedup, first wins), clear the stopped + crash flags — “A fresh process means a future crash is a new fact” — then announce plugin_state: reloaded state.rs:621-678.

What callers see: a call that missed the shutdown gets a synthetic plugin '…' disconnected error at the call site host.rs:811-816, and cancelled calls return error tool results the model can retry — the log stays honest (DESIGN.md:2071). What survives: the plugin's KV store, because it's SQLite-backed per plugin namespace host.rs:96-101 · db.rs:566-573. What doesn't: process memory, by design.

same contract via host ops (plugin_reload, plugin_start, plugin_stop) — an agent can repair its own tools host_api.rs:262-280. And zero-restart re-declaration: send {"t":"declare", …} to swap your tools, hooks and capabilities live — “plugin updates its tools/hooks/capabilities at runtime” codec.rs:124-136 · state.rs:1103-1152.

the config — debounced by design

The watcher is an mtime poll every 2s with a settle rule: a change reloads only once the timestamp has been stable for a full interval — “an editor doing delete-then-write would otherwise trigger a reload on the gap, against a file that does not exist yet” watch.rs:41-90. On reload, the providers, model registry, default model and provider-plugin generation are swapped in place state.rs:853-913; in-flight turns keep their cloned provider and finish on the old one. On error: “Keep serving the old config. A syntax error mid-edit is expected and must not take the server down” watch.rs:138-140.

what does not hot reload (exact list)

new [[plugin]] entries — the config watcher explicitly skips them state.rs:844-846; use POST /plugin/load {"from_config":true} (spawns only the new ones) or restart.

a crashed plugin — there is no supervisor and no auto-respawn. The health scan announces plugin_state: crashed once state.rs:478-502, and its tools refuse with blocked: tool '…' belongs to a plugin that is currently stopped. Start the plugin again before retrying — “so the agent can restart the plugin instead of giving up on the capability” exec.rs:619-631.

[policy] mode and [server] idle_exit_secs — read at startup only state.rs:844-846 (docs agree: CONFIG.md:94).

the embedded default UI — assets/tui/*.lua ship via include_str! and need a rebuild default_config.rs:26-59; the editable surface is the copy seeded to ~/.kn9t/tui/. And no SIGHUP anywhere: reload is a file save or an explicit call, never a magic signal.

08 — the terminal UI

Lua decides where, Rust decides how

The TUI never imports kn9t-core — HTTP + SSE only kn9t-tui/Cargo.toml:7. Its whole layout is one Lua program returning a widget tree: “the mechanism/policy boundary: Lua decides where, Rust how (markdown, highlighting, scroll maths, render cache)” render.rs:271-272.

  • 5 native views rendered by Rust at Lua-chosen rectangles: transcript · input · status · explorer · viewer widgets.rs:152. If render_ui fails, you get the error shell — “There is deliberately no second Rust layout” render.rs:122-134.

10 — docs vs source

Where the docs drift (the source wins)

This page was written from the code and checked against the docs afterwards. Most of it matches — but here is exactly where they disagree, so you know which one we trusted.

  • The crate graph in AGENTS.md shows 5 crates. The workspace has 15 members (14 crates + xtask) — incl. kn9t-store, kn9t-react, kn9t-plugin, kn9t-provider-* Cargo.toml:3-20.
  • There is no Policy trait. Docs mention traits (Provider, Tool, Store, Policy); the code has Store · Tool · Provider · Compactor · Approver · PluginKv · EventSink plus policy structs, and ADR-0008 moved the judgement to a policy plugin traits.rs · policy.rs:1-17.
  • “9 hooks” = 8 + 1. HookName has 8 variants event.rs:31-39; the ninth thing is the on_event bus subscription, which the spec counts separately (spec/08-plugin.md:65-82).
  • Native views: docs say 3 (transcript, input, status); the code has 5 — explorer and viewer are native too widgets.rs:152.
